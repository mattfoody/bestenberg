# DECISIONS.md

Log of non-obvious choices. Newest at the bottom. Format: date — decision — reason.

- 2026-10-07 — Editor app lives in `wp/editor/` as a pnpm workspace package (`@bestenberg/editor`) and builds into `wp/plugin/build/editor/`. — The plugin directory is the only thing shipped; keeping build output inside it means wp-env maps one folder.
- 2026-10-07 — TS packages build with tsup (ESM + d.ts); a single root Vitest config runs all package tests. — One command for all unit tests; per-package configs add noise.
- 2026-10-07 — wp-env pins WordPress via the official `wordpress-7.1.zip` URL and WooCommerce via the `woocommerce.zip` (latest stable) URL so the plugin folder is `woocommerce`. — Matches PLAN minimum (7.1); Woo follows stable releases.
- 2026-10-07 — Local Node is 22 in some environments; `.nvmrc` stays 20 (minimum) and CI tests on 20. — Lowest supported version is what CI must prove.
- 2026-10-07 — Lockfiles committed by Matt after the first local install; CI now installs with `--frozen-lockfile` and setup-node caching. — Reproducible CI.
- 2026-10-07 — TypeScript `~5.9` and ESLint 9 (flat config) rather than TS 6 / ESLint 10. — typescript-eslint support for the newest majors was unverified; upgrade together later.
- 2026-10-07 — PHPUnit 9.6 + Yoast polyfills, run inside wp-env's tests container. — The WordPress core test library targets PHPUnit 9; polyfills keep tests forward-compatible.
- 2026-10-07 — Full-screen editor page hides WP admin chrome with a body class + CSS rather than a custom admin template. — Least invasive; keeps admin notices, capabilities and screen handling standard.
- 2026-10-07 — ESLint `no-restricted-imports` enforces "no `@wordpress/*` in packages/ except adapter-blocks". — Makes PLAN.md §2.6 a build error instead of a convention.
- 2026-10-07 — Token references in documents are full refs (`"space.4"`, `"color.primary"`), typed from generated name lists. — Self-describing for AI and validation; matches SCHEMA.md §2.
- 2026-10-07 — Packages expose a `source` export condition; TS (`customConditions`) and Vitest (aliases) use sources, tsup builds against sibling `dist` via `tsconfig.build.json`. — Typecheck and tests work before anything is built; published output stays standard.
- 2026-10-07 — Width tokens map to `bb:container-{name}` (width 100%, max-width, centered) rather than Tailwind's `max-w-*`. — One class does what a container needs; the name says so.
- 2026-10-07 — `bb:flex` / `bb:grid` also reset `margin-block-start` on children. — WordPress flow layout adds block-gap margins to children; inside flex/grid, spacing must come from `gap` only.
- 2026-10-07 — Visibility uses exact-range classes (`bb:max-md:hidden`, `bb:md:max-lg:hidden`, `bb:lg:hidden`) with `!important`. — "Hide on tablet" must not cascade to desktop, and must beat display utilities.
- 2026-10-07 — Utility map ships as both `utilities.map.php` (runtime, opcache-friendly) and `.json` (tooling/tests). — No JSON decode per request.
- 2026-10-07 — The PHP collector reads `bb:` classes from each block's `className` attribute (via `render_block`), not by re-parsing HTML. — Exact and cheap; nested blocks would otherwise be re-scanned at every level. `record_html()` remains for other sources.
- 2026-10-07 — Used utilities go out via `wp_add_inline_style` at `wp_enqueue_scripts` (block themes render the template before `wp_head`), plus a late footer style for classes first seen afterwards. — Standard WP asset API, CSS in <head>, nothing lost on classic themes.
- 2026-10-07 — `composer.lock` is refreshed by the manual "Refresh composer.lock" workflow (PHP 8.1). — Keeps the lock resolvable for the minimum PHP version; no local Composer needed.
- 2026-10-11 — The adapter implements the block grammar and the nine core blocks' save/extract itself instead of depending on @wordpress/blocks in Node. — Runs anywhere (server, AI, tests) with no DOM or WordPress; the real editor validates its output in e2e, so drift from core is caught in CI.
- 2026-10-11 — Block conversion lives in adapter-blocks keyed by component type; the registry only names the block and, for own blocks, describes the element. — Keeps the registry WP-agnostic (PLAN §2.2).
- 2026-10-11 — Utility classes for core blocks are added at render time from the `bestenberg` attribute, not saved in `className`. — Content stays free of Bestenberg class names, so naming can change without migrations and editing in core Gutenberg cannot corrupt them.
- 2026-10-11 — Own-block attribute for the node id is `bbId` (core blocks: `bestenberg.id`). — Avoids clashing with any `id` a future WordPress feature may add.
- 2026-10-11 — Property tests use a seeded generator written in the test file instead of fast-check. — No new dependency (CLAUDE.md); seeds make failures reproducible.
- 2026-10-11 — Image props are `src`, `alt`, `mediaId`; width/height removed. — Size comes from width/aspect tokens; core image width attributes would reintroduce free values.
- 2026-10-11 — Added `height` style key (`bb:h-*`) for the spacer block. — A spacer needs an explicit token height; padding hacks are fragile.
- 2026-10-11 — Button variants are stored as `is-style-{variant}` className, including `primary`. — Exact round-trip; absent variant stays absent.
- 2026-10-11 — Lists are `list` → `list-item` children (nested lists inside items), quotes hold `text` children; buttons must sit in a `button-group`. — Mirrors core block structure, so conversion is 1:1.
- 2026-10-11 — e2e checks adapter output structurally (editor validity, frontend CSS) rather than with a stored HTML snapshot; the generated `adapter-page.html` fixture is the reviewable snapshot and CI fails if it is stale. — Snapshot files cannot be produced in this workspace; the fixture serves the same purpose.
- 2026-10-12 — Updates are self-hosted: plugin and theme declare `Update URI`, and Bestenberg's own updater answers `update_plugins_<host>`/`update_themes_<host>` from static `info.json` files on Matt's VPS. — Native WordPress mechanism (no update library dependency); works for Matt's sites and customers alike; pulled forward from M9. Licensing/token checks come later.
- 2026-10-12 — Releases are tag-driven: `pnpm release:bump` sets all version strings and tags; the Release workflow builds, rsyncs zips then info.json to the VPS, and creates a GitHub release. The same scripts run locally. — One path for CI and manual releases; zips before metadata so sites never see a missing package.
- 2026-11-15 — The editor has its own canvas instead of embedding the Gutenberg block editor: the schema document is the editing model, rendered into an iframe that loads the real frontend (theme, header, footer, CSS). — Full control of the UI (the product's point), true WYSIWYG, and no dependency on block-editor internals; Gutenberg remains the storage and render layer.
- 2026-11-15 — The canvas renders nodes in the browser with `renderNodes()` (TS mirror of the PHP render), not by asking PHP on every edit. — Instant feedback; parity is enforced by shared fixtures and e2e. Raw blocks are the exception and are rendered by `POST bestenberg/v1/render`.
- 2026-11-15 — Style changes default to "all sizes" (written to `base`) on every viewport; the user opts in to "this size and up". — People previewing on desktop expect a colour change to apply everywhere; writing desktop-only overrides by default produces pages that look unstyled on phones.
- 2026-11-15 — Undo history is a list of immutable documents (limit 100); typing replaces the latest entry instead of adding one per keystroke. — Simple and correct; documents are small.
- 2026-11-15 — The editor uses only `@wordpress/element`, `@wordpress/api-fetch` and `wp.media`; no `@wordpress/components`. — Own UI, small bundle, fewer moving parts across WordPress releases.
- 2026-11-15 — Rich-text controls are not shown in the inspector; text is edited on the canvas. — One obvious place to edit text; no HTML source shown to customers.
- 2026-11-15 — `bin/wp-sqlite.sh` runs WordPress from GitHub with SQLite for environments without Docker. — Lets the editor be developed and e2e-tested where wp-env cannot run; CI still uses wp-env.
- 2026-11-15 — Library sections are functions that build schema nodes (`PATTERNS` in `@bestenberg/schema`), not stored block markup or WordPress block patterns. — WP-agnostic, validated by the same schema as everything else, fresh ids per insert, and directly usable as AI examples.
- 2026-11-15 — The AI pipeline (prompts, normalizing, token snapping, validation, repair) runs in TypeScript in the editor; PHP only forwards single model calls to the WordPress AI Client. — One implementation of the pipeline, shared with tests and the future hosted service; PHP has no schema validator to keep in sync.
- 2026-11-15 — Model calls are stateless: each repair round sends the request, the previous answer and the problems in one prompt. — Works with every provider without conversation-history APIs; simple to proxy and to test.
- 2026-11-15 — The model is asked for JSON in the prompt rather than through provider-enforced structured output. — The document schema is recursive and provider support for such schemas varies; normalizing plus validation and repair gives the same guarantee everywhere.
- 2026-11-15 — AI results are committed as one undo step and reviewed with Keep / Discard (discard = undo) instead of a separate diff view. — The canvas already is the preview; one mechanism, nothing saved until the user saves.
- 2026-11-15 — Only a read-only ability (`bestenberg/get-design-system`) is registered for now; abilities that create or restyle pages server-side are deferred. — They need the schema → blocks adapter and validator in PHP (or the hosted service); exposing a write ability without validation would break the schema-first principle.
- 2026-11-15 — The AI route accepts screenshots only as inline data URLs. — The server never fetches a URL chosen by the user (no SSRF surface).
- 2026-11-15 — The eval harness renders pages standalone (same `renderNodes()` and token CSS as the canvas, no WordPress) and scores visual similarity relative to a blank page, averaged with a structure score. — Fast and runnable anywhere; raw pixel difference rates a nearly empty page above 0.8 because pages are mostly background.
- 2026-11-15 — CI runs the harness with an oracle and a degraded provider only; real models run on demand with `--provider=openai`. — CI must be deterministic and free; the oracle run proves the harness and the degraded run proves the metric can fail.
- 2026-11-15 — Site, post and store data (menu, post title, product grid, cart, checkout) are WordPress/WooCommerce blocks placed as raw nodes, chosen from a curated list (`DYNAMIC_BLOCKS`); Bestenberg does not re-implement them as components. — WooCommerce keeps owning commerce logic and its markup changes between releases; Bestenberg owns the layout around it. Their inner settings stay in WordPress for now.
- 2026-11-15 — The base theme's templates are generated from schema documents, not hand-written HTML. — Every template is guaranteed to open in the editor and to validate; one source of truth.
- 2026-11-15 — Templates and parts are edited on a bare canvas page (site styles, no header/footer) and need `edit_theme_options`. — A template has no single URL to load; previews of post blocks use a published example of the right type.
- 2026-11-15 — Client mode is decided by capability: users who cannot `edit_theme_options` (Editors) are clients; Administrators design and can preview client mode. — Uses WordPress roles as they are; no new roles or settings screens.
- 2026-11-15 — Only "locked completely" (`all`) is inherited by children; "items can be arranged" (`none`) applies to direct children only. — Opening a list of cards should not also make every heading inside a card deletable.
- 2026-11-15 — In open groups clients duplicate, reorder and remove existing items; they get no component inserter. — "Another one like this" is what content editors need, and it cannot produce off-design layouts.
- 2026-11-15 — Client mode is enforced in the editor (one `can()` check in every action), not on the server. — Anyone who may edit a page in WordPress can already change its blocks in the block editor; client mode protects against accidents, it is not a security boundary. A server-side diff check can be added if sites need it.
- 2026-11-15 — The license key gates nothing in the plugin; it is only sent to the update server, which may require it for downloads. — The code is GPL and sites must never break because a license lapsed; what is sold is updates and support.
- 2026-11-15 — The key travels in a request header, not in the URL. — URLs end up in server logs and proxies.
- 2026-11-15 — The demo site is generated from the section library and imported as ordinary pages, marked with post meta; existing demo pages are never overwritten. — Demonstrates the real product path (schema → blocks), is reproducible, and is safe to run twice.
- 2026-11-15 — Demo pictures are SVG files shipped in the plugin and referenced by URL, not imported into the media library. — No network access or uploads needed at import; users replace them with their own images.
